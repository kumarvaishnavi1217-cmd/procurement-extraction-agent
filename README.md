# Procurement Document Extraction Agent

An LLM pipeline that turns unstructured supplier **quotes and invoices (PDF)** into a validated schema: supplier, document number, date, currency, and line items with **part number, quantity, unit price** and totals. Values the system can't trust go to a **human-review queue**, field by field. An **evaluation harness** measures field-level accuracy on a labelled document set.

Python 3.12 · Claude API (`anthropic` SDK, structured outputs) · FastAPI · PostgreSQL · SQLAlchemy 2 · pytest + Testcontainers

## How it works

```
PDF ──► POST /documents
          │  size / type checks, SHA-256 dedupe
          ▼
      Claude (native PDF input, structured output → Pydantic schema)
          │  every field = value + confidence + verbatim evidence
          ▼
      Validation rules  ──►  per-field confidence
          │                        │
          ▼                        ▼
   PostgreSQL               below threshold ──► review_tasks (human queue)
   documents / extractions                       POST /review-tasks/{id}/resolve
```

**Why not trust the model's confidence?** LLM self-reported confidence is poorly calibrated. Each field also carries an `evidence` snippet copied from the document, and deterministic rules cap the confidence when something doesn't add up:

| Rule | Catches |
|---|---|
| Evidence must appear in the PDF text layer | hallucinated values |
| The number in the value must match the number in the evidence (handles `1,234.50` / `1.234,50` / `1'234.50`) | misread or transposed digits |
| `qty × unit price = line total`, `Σ lines = subtotal`, `total ≥ subtotal` | misread numbers, skipped line items |
| Supplier must not be our own company (`PROCEX_BUYER_NAMES`) | bill-to party taken as supplier |
| Document number evidence must not be labelled PO / order no. | PO number taken as invoice number |
| Required fields, ISO date, ISO 4217 currency, part-number format | missing / malformed values |
| No text layer (scanned PDF) | nothing to verify against, so everything is reviewed |

Any field whose final confidence is below `PROCEX_REVIEW_THRESHOLD` (default 0.8) becomes a review task. When a reviewer corrects a field, the stored data is updated; the model's raw output is kept unchanged for auditing.

## Evaluation harness

```bash
procex-eval --extractor claude                         # live: needs ANTHROPIC_API_KEY
procex-eval --extractor fixture                        # offline, simulated model output
procex-eval --extractor claude --out eval-report.json  # JSON report
```

It reports per-field accuracy plus the two numbers that matter for an extraction pipeline with a review step:
- **auto-accepted accuracy:** how correct the values are that skip human review
- **error catch rate:** what share of wrong values the review queue catches

It also reports review rate, tokens, latency and cost per document. Use it to tune the prompt, the review threshold, the model, and `PROCEX_EFFORT`.

The labelled set (`eval/dataset`) is **12 synthetic quotes and invoices** generated by `eval/generate_dataset.py`. They vary layout, number format (US/EU), date format (ISO, `14.03.2026`, `14 March 2026`, ambiguous `03/04/2026`), currency and tax. `eval/fixtures` holds **simulated** model outputs with typical LLM mistakes injected: buyer taken as supplier, PO number taken as invoice number, a quantity misread by a factor of 10, an ambiguous date, a hallucinated price, and a skipped line item.

Offline result on the fixtures:

| | before the PO/buyer rules | after |
|---|---|---|
| auto-accepted accuracy | 97.3 % | **100 %** |
| error catch rate | 33.3 % | **100 %** |
| review rate | 3.9 % | 6.5 % |

These numbers show that the validation rules and the scoring work. They are **not** a measurement of Claude's accuracy. For that, run `procex-eval --extractor claude`, or the `live-eval` CI job with an `ANTHROPIC_API_KEY` secret, ideally on real (anonymised) documents.

## API

| Method | Path | |
|---|---|---|
| POST | `/documents` (multipart `file`) | extract; `201`, or `200` if this exact file was already processed |
| GET | `/documents?status=needs_review` | list (`auto_approved`, `needs_review`, `reviewed`, `failed`) |
| GET | `/documents/{id}` | data, per-field confidence and issues, token usage, open tasks |
| GET | `/review-tasks?status=open` | review queue, least confident first |
| POST | `/review-tasks/{id}/resolve` | `{"value": ..., "reviewer": "anna"}`; send the extracted value to confirm it |
| GET | `/health` | DB check |

OpenAPI docs at `/docs`. Logs are JSON, one line per event, with a request id that's also returned as `X-Request-ID`. They cover model, LLM request id, tokens, latency and flagged fields.

## Run

```bash
cp .env.example .env               # add ANTHROPIC_API_KEY
docker compose up --build
curl -F file=@eval/dataset/doc02.pdf localhost:8000/documents
curl localhost:8000/review-tasks
```

No API key? `PROCEX_EXTRACTOR=fixture docker compose up --build` replays the stored outputs for the PDFs in `eval/dataset`.

Model: `claude-opus-5-5` by default (`PROCEX_MODEL`), with effort `medium` (`PROCEX_EFFORT`). Server-side refusal fallback is enabled. Refusals, truncation and missing credentials are recorded as `failed` documents rather than crashing the request.

## Tests

```bash
pip install -e ".[dev]"
pytest            # needs Docker for PostgreSQL
```

- **Validation rules:** one test per rule, number-format parsing.
- **Claude request:** PDF document block, structured output schema, effort, fallback, refusal / truncation / missing credentials, all against a stub client.
- **API:** runs on real PostgreSQL via Testcontainers. Covers upload, dedupe, the review flow end to end, ordering, invalid input, and failed extraction.
- **Regression:** a snapshot of which fields get flagged on every labelled document, plus a quality gate (auto-accepted accuracy and catch rate) that fails CI if a change makes things worse. After an intentional change, regenerate the snapshot with `UPDATE_SNAPSHOTS=1 pytest`.

CI (`.github/workflows/ci.yml`) runs ruff, strict mypy, the tests, the offline eval gate and a Docker build. You can trigger a live eval against Claude manually.

## Limitations / next steps
- Extraction is synchronous inside the request. At volume, move it to a queue worker, and use the Message Batches API for bulk backfills (50% cheaper).
- Schema creation uses `create_all`. Add Alembic migrations before the schema needs to change in production.
- The review API has no authentication. Put it behind the company's SSO before real use.
